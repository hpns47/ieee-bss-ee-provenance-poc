## 0. Контекст и цель одним абзацем

Есть рабочий прототип: пайплайн из 9 стадий (data_acquisition_s2 → data_acquisition_s1 → pearson_corr_period1 → pearson_corr_period2 → delta_corr → r_t → moran_index → risk_index → change_mask), каждая стадия хешируется в Merkle-leaf, агрегируется в root, сравнивается с naive baseline (подпись только финального output). Сейчас tamper-detection проверен только **на одном эпизоде, одной магнитуде атаки, на одной атакуемой стадии (change_mask)**. Это самое слабое место статьи по мнению рецензента. Задача: превратить это в статистически значимый эксперимент — прогнать атаки по сетке параметров, получить проценты (detection rate, localization accuracy), и построить по ним новые графики. Плюс закрыть ещё один явно названный в Limitations пробел — Type-1 (data-level) атака сейчас вообще не тестируется эмпирически, только "адресуется структурно".

## 1. Что дорабатывать в коде — Attack Sensitivity Sweep

### 1.1. Общая идея

Взять существующий synthetic harness (тот, что уже генерирует reference episode с seed=42) и обернуть его в цикл, который:
1. Генерирует baseline episode (честный, без атаки) — уже есть.
2. Применяет контролируемую атаку заданного типа/магнитуды/стадии.
3. Прогоняет verification (Merkle-proof check + naive baseline check).
4. Записывает результат (detected/not, localized/not, к какой стадии).
5. Повторяет для сетки параметров × N случайных seed'ов.

### 1.2. Параметры сетки

**Тип атаки:**
- `type2_parameter` — изменение одного из governance-параметров (α, β, λ, τ) без соответствующей PARAMETER_CHANGE записи в governance-log
- `type3_output` — прямое редактирование output-значения стадии без пересчёта зависимостей
- `type1_data` — подмена scene_ids_hash / n_scenes на стадии data_acquisition_s2 или data_acquisition_s1 без реального пересчёта downstream (это новый тест — раньше был только "structurally addressed", не эмпирический; закрыть именно этот пробел из Limitations)

**Атакуемая стадия (для type2 и type3):** пройтись по всем 9 стадиям, не только по change_mask, как сейчас. Для type2 естественная атака — на стадии с параметрами: risk_index (α, β, λ) и change_mask (τ). Для type3 — атака на output любой из 9 стадий.

**Магнитуда атаки:**
- Для τ (change_mask): абсолютное смещение Δτ ∈ {0.02, 0.05, 0.1, 0.15, 0.2, 0.3} (и в плюс, и в минус от базового 0.4)
- Для α, β, λ (risk_index): относительное смещение ∈ {5%, 10%, 20%, 30%, 50%} от исходного значения, с перенормировкой так, чтобы сумма оставалась осмысленной (или без перенормировки — задокументировать выбор)
- Для type3 (output-редактирование): относительное искажение значения output ∈ {1%, 5%, 10%, 25%, 50%} — важно включить и маленькие магнитуды (1-5%), чтобы показать чувствительность метода к тонким подменам, а не только к грубым
- Для type1 (data-level): бинарно — либо подменённый scene_ids_hash (симуляция подмены снимка), либо нет

**Повторы:** 30–50 случайных seed'ов на каждую комбинацию (тип × стадия × магнитуда), чтобы получить проценты, а не единичный результат. Итоговая сетка ~ 2 (type2/type3 стадии-цели) × 9 стадий × 5-6 магнитуд × 30-50 seed'ов — это не тяжело вычислительно (пайплайн уже сейчас <11мс), должно отработать за минуты.

### 1.3. Метрики на выходе (на каждую комбинацию type × stage × magnitude)

```
{
  "attack_type": "type2_parameter" | "type3_output" | "type1_data",
  "target_stage": "risk_index" | "change_mask" | ... (любая из 9),
  "magnitude": <число или относительная величина>,
  "n_trials": 30,
  "proposed_detected_count": <int>,
  "proposed_localized_correct_count": <int>,
  "naive_detected_count": <int>,
  "naive_localized_correct_count": <int>,
  "proposed_detection_rate": <float, 0-1>,
  "proposed_localization_accuracy": <float, 0-1>,
  "naive_detection_rate": <float, 0-1>
}
```

Сохранить как единый `attack_sweep_results.json` — массив таких объектов, по одному на комбинацию.

### 1.4. Что это даёт для статьи

Заменяет фразу в Limitations "a broader sweep over attack magnitudes... is needed" на реальную секцию с цифрами — то есть закрывает собственное честно признанное ограничение. Плюс закрывает второй пробел (Type-1 эмпирически не тестировался).

## 2. Новые графики — точная спецификация

Все графики: 300 DPI, serif-шрифт (Times New Roman / DejaVu Serif fallback), подписи на английском (для статьи), без длинных тире, размер под IEEE single-column (~3.3-3.5 in ширина) или double-column (~7 in), где уместно.

### Fig. A — Detection rate vs attack magnitude
- Line chart. X = магнитуда атаки (нормализованная, например % от исходного значения параметра). Y = detection rate (0-100%).
- Две линии: Proposed (Merkle) vs Naive baseline, для Type-2 атаки на τ (или risk_index parameters) — самый показательный случай, поскольку naive baseline должен быть плоской линией на 0% (структурно слеп к параметрам), а Proposed — на 100% на всех магнитудах.
- Если наберётся интересная динамика (например, detection rate proposed падает на очень малых магнитудах из-за округления/шума) — это тоже ценно показать честно, не приукрашивать.

### Fig. B — Localization accuracy heatmap
- Heatmap 9×2 (9 стадий по оси Y, Type-2/Type-3 по оси X, или наоборот) — ячейка = % корректной локализации атакованной стадии.
- Цель: показать, что метод одинаково хорошо локализует атаку **на любой стадии**, а не только на change_mask (сейчас все примеры в статье бьют именно в change_mask, что выглядит как совпадение, а не системное свойство).

### Fig. C — Type-1 (data-level) detection — новый график, которого раньше не было
- Простой bar chart или таблица: detection rate для подмены scene_ids на S2 vs S1, proposed vs naive.
- Закрывает явно названный пробел в Limitations.

### Fig. D — Latency vs scale (log-log)
- Из уже существующей таблицы (100м/30м/10м, pipeline_ms и anchor_ms). Построить log-log line plot вместо таблицы — нагляднее показывает, что anchoring overhead растёт медленнее, чем pipeline compute при увеличении разрешения.
- Если получится добавить ещё 1-2 промежуточные точки разрешения (например 50м, 20м) — график станет убедительнее (5 точек вместо 3), но это опционально, не критично.

### Fig. E — On-chain storage growth over monitoring period
- Line chart (не таблица, как сейчас) из данных Table III: X = время (1/2/5 лет), Y = накопленное on-chain хранилище (KB), три линии — monthly / bi-weekly / weekly cadence.
- Показывает O(episodes) масштабируемость наглядно.
